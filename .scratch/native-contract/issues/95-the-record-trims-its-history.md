# 95: The record trims its history

Spec: [record 0008](../../../docs/adr/0008-the-certificate-checks-each-window-as-the-run-goes.md), the [solver contract](../../../docs/architecture/solver-contract.md)'s section 5 and its Checkpoint paragraph, and `crates/ng-record/src/history.rs`

Type: task

Status: resolved

Blocked by: 94

Blocks: [body ticket 28](../../body/issues/28-two-synthetic-days.md)

**Why.** The first milestone (SRS invariant I19) holds the whole body for 48 hours under its certificate, and that run cannot keep every ledger chunk: record 0008 puts one 48 h course of the slice at 296 to 342 GB, and at 74 to 86 GB compressed. [Native-contract 94](94-the-certificate-folds-as-the-run-goes.md) builds the fold, which judges each window as the run goes. The fold alone frees no space: on main a store that keeps a link keeps it complete, compacted or not, and the day runner's `KeepsNothing` keeps none. Record 0008 says what a run keeps in their place, main holds none of it, and no other ticket owns it. It lands before the whole body's 48 h run.

Record 0008 rules the order: before any history is trimmed, the fold matches `certify` and the independent oracle on every window shape. The first box holds it.

- [x] Before anything is trimmed, the fold matches `certify` and the independent oracle on every window shape main then has. For the fixed windows native-contract 94's tests show it. For the windows between edges, where [native-contract 85](85-the-certificates-windows-end-on-breath-edges.md) has merged, a test this ticket names or adds shows it
- [x] During a run the history store keeps a rolling day of complete links, reaching back to the checkpoint before the oldest window still open, so a failing window's span is whole when the fold refuses it
- [x] After a run the store keeps a witness for each step, 96 bytes: the step's seal, its image digest and its ledger digest. Each seal recomputes from the seal before it, the revision and those two digests, with the hash the run already uses. It also keeps a checkpoint each simulated minute with its head link
- [x] The flight recorder: on the first closure or drift failure, a replay divergence, an engine fault or a store failure, the run keeps the original links from the checkpoint before the failing window to the last head
- [x] What a finished run let go is checked as well as what it kept. After a run that passed, a listing of the store shows the witnesses, the checkpoints and their head links, and no other complete link, and the run still has its certificate over every window and its event log. After a run that failed it shows the flight recorder's span as well, the one span that is still checked from the store alone
- [x] A trimmed `restore` checks every seal back to admission, the checkpoint's head link and its image, reparses the ledger of no discarded step, and takes the run's opening time from the record's opening, which a witness does not hold
- [x] A revision between checkpoints replays forward from the checkpoint before it, and every replay gate keeps its live comparison on fresh cores. A regeneration on the build that made the run, which the run's evidence names, is checked step by step against the witnesses and gives back the parse of each discarded step's ledger. One that no longer reproduces its seals is reported as a finding
- [x] `certify` runs no core. A trimmed run's certificate is recomputed only from a rerun of the pinned build or a regenerated history, and a corrected healthy-range set or policy is rechecked the same way. Record 0008's one exception has a test: under the same basis, windows and closure limits, a complete run that passed closure shows from the worst drift it kept for each combination that it passes a loosened drift bound, and a failure under the new bound needs the rerun to name its first window
- [x] Links and checkpoints that an earlier build wrote still load
- [x] What a course keeps during the run and after it, in bytes that a run shows: at least a simulated hour of the body main then has, scaled to 48 h beside record 0008's arithmetic for the slice, which is 3.05 to 3.52 GB of witnesses, 111 MB of checkpoints, and 37 to 43 GB of compressed links for the rolling day plus 26 to 30 MB back to its checkpoint. The 48 h course's own bytes are [body ticket 28](../../body/issues/28-two-synthetic-days.md)'s to report
- [x] A mutant row for each rule

The stored forms are new state in the record, so the ticket starts with their design: what a witness and a flight recorder's span are in the store, which seal or digest names each of their fields, how a store tells a trimmed run from a complete one, and how `certify` reports a history it cannot recompute. On main a certificate's result for each combination already holds its worst drift (`worst_drift` in `crates/ng-validate/src/certificate.rs`).

**Non-goals:** the fold and its evaluator (native-contract 94), windows between edges (native-contract 85), a store of past state or readings, which record 0008 leaves to a replay, and any change to what a certificate holds.

**The body's bytes, measured before this ticket starts.** On main's whole body at `e2d5c6ba`, an accepted step's link is 131,920 bytes raw and about 65,960 after `ng_record::compact`: 65,972 on average over a 30 s run's 5,851 links and 65,961 over a 2,900 s run's 562,271, since `compact` keeps a link whole when it cannot use the one before. A compressing filesystem saved about 5% more. The body accepts 349,076 steps in its first 1,800 s, awake, and 348,830 in the next 1,800 s, asleep. So an hour is about 92 GB raw and 46 GB compacted, and a 48 h course about 4.4 TB and 2.2 TB. Record 0008's 296 to 342 GB is the slice in this same compacted form ([native-contract 25](25-history-on-disk.md)), so the body's course is 6.5 to 7.5 times the slice's. The record's 74 to 86 GB, and its 37 to 43 GB for the rolling day, add a delta between links and zstd, which this measurement did not apply to the body. So the body's rolling day under the record's codec is not measured. Compacted alone it is about 1.1 TB, and the build worker that measured it has 133 GB free. This ticket's design opens by measuring the body's links under the record's codec and saying where a rolling day of them is kept. If no worker holds it, that is a question for a new record before any box here changes: record 0008 keeps the original links because a faulty core may not regenerate them. Certifying from a disk store took 1.47 ms a link.

## Answer

### Stored forms and verification seam

- **96-byte chain witness (`ng_record::Witness` and `ng_validate::WitnessEntry`):** `Witness` holds `(previous, image, ledger)` digests (96 bytes exact) and recomputes `seal(hash, revision)` with the run's hash (`V1` SHA-256 or `V2` BLAKE2b), reusing the ledger digest `History::linked` already computes with zero extra hashing. Sequential store storage keeps `(seal, image, ledger)` (96 bytes per step) plus one 32-byte `origin`, resolving `previous` from the preceding entry. `HistoryStore` gains default-implemented `resolve_witness` and `keep_with_witness`, preserving source compatibility for every existing store.
- **Checkpoint trailer and backward compatibility (`crates/ng-record/src/checkpoint.rs`):** `ngcheck1` (SHA-256) and `ngcheck2` (BLAKE2b) magics stay unchanged. On `ngcheck2` checkpoints at `revision > 0`, the body appends `opened: SimTime` (8 bytes), `head_link_len: u64` (8 bytes) and the canonical head link bytes after `origin`, covered by the header's raw SHA-256. Legacy `ngcheck1` and `ngcheck2` checkpoints ending at `origin` still load (`prior_shape` keeps exact `ngcheck1` byte identity; `history_trim::earlier_v2_checkpoints_without_trailer_still_load_and_continue` pins legacy `ngcheck2` loading).
- **Trimmed `restore`, `History::holds` and `HistoryTrimmed`:** `restore` verifies and parses the checkpoint's head link against `header.seal` and `image.digest()`, checks `opened` invariants (and cross-checks `opened` against `parent` on `rewind`/`recover`), and walks `rev - 1 ..= 1` to `origin.seal` through verified witnesses without calling `store.resolve` or reparsing discarded ledgers. `History::holds` verifies each witness seal while walking back. `Walk::read` distinguishes a trimmed step (`CheckpointError::HistoryTrimmed { seal }`) from a missing step (`HistoryMissing`) and a tampered witness or link (`HistoryAltered`).
- **Rolling store, flight recorder, regeneration and loosened-drift recheck (`crates/ng-validate/src/trim.rs`, `certificate.rs`):**
  - `ConservationFeed::oldest_retained_revision` and `CertificateFold::{failure, oldest_open_window_start, oldest_retained_revision, drift_tally}` let `RollingStore` trim complete links safely across 64-link page boundaries and latch `FlightRecorderSpan` immediately on the first trigger (closure, drift, edge-drift or stopped-rhythm failure even before `coverage_ns` is reached, replay divergence, engine fault or store failure).
  - `RollingStore::finish` removes all complete links outside any latched flight recorder span and exposes `StoreListing` verifying both kept items and absent links. `ng_record::retained_span` plus `certify_flight_recorder` verify the witness prefix and retained links from the store alone without running a core.
  - `regenerate` resumes any checkpoint, at admission or a later minute, on a fresh core of the pinned build named in evidence, through a `ReplayStore` that reads ancestors' witnesses from the run's store and keeps regenerated links in a separate sink, so the chain it is checked against never moves. It checks every step against the witness for its expected seal, so a revision between checkpoints replays forward from the checkpoint before it, a regeneration from admission restores full ledger parsing for `certify`, and any divergence is a `RegenerationFinding`.
  - `RollingStore` keys complete links by revision and seal, so every session of a run may share one store, and a store failure or engine fault keeps the flight recorder's span from the checkpoint before the window open when it happened.
  - `DriftTally::recheck` and `Certificate::recheck_drift` recheck a revised drift bound under the same basis, windows, row rounding, edge policy and closure limits without changing `Certificate`'s fields, returning `DriftRecheck::NeedsRerun` whenever a bound fails so a rerun names the first failing window.
  - Pre-trim edge-window parity (`native-contract 85`) is pinned by `rhythm_certificate::the_live_fold_matches_certify_and_the_oracle_on_every_window_between_edges`, all trimming rules by `crates/ng-validate/tests/history_trim.rs`, and 22 mutant rows in `tools/gate/mutants.d/nc95-history-trim.toml` (all 22 caught; 749 of 749 workspace mutant rows apply).
